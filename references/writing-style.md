# 写作与代码风格

报告要像"一个学生做完实验后写的"，不是"一份产品文档"，也不是"AI 总结"。
这份文档管三件事：代码怎么贴、正文怎么写、总结怎么收尾。

## 一、代码：零注释

**规则**：所有贴进报告的代码，不出现任何注释。

| 语言 | 禁止出现 |
| --- | --- |
| C / C++ / Java / JS / TS / Go | `//`、`/* */` |
| Python | `#`（含 `# -*- coding -*-`）、三引号文档字符串 |
| SQL | `--`、`/* */` |
| HTML / XML | `<!-- -->` |
| Shell | `#`（她 bang `#!/bin/bash` 只在完整脚本首行可保留） |

替代做法：

- 用变量名和方法名表达意图：`calculateAverage()` 不需要注释解释。
- 用短小的函数代替大段流程：每个函数只做一件事。
- 需要解释的地方写进正文段落，不要塞进代码。

**唯一例外**：如果一个数字或魔法值必须解释（如 `4096` 是缓冲区大小），把它变成常量 `BUFFER_SIZE = 4096`，而不是加注释。

其他要求：

- 贴的是最终跑通的那版，不要留被注释掉的旧代码、`print` 调试输出、`TODO`。
- 缩进统一 4 空格（Python）/ 与语言惯例一致。
- 单段 15~60 行；超过就拆。
- 完整源码放工程目录或附录，正文只留关键段。

## 二、正文口吻

三条：

1. **用"本实验"和"我"，不用"本文"和"我们团队"。** 实验报告不是论文，"本文提出了一种方法"太重。
2. **一句话说一件事。** 超过 40 字的句子拆开。
3. **少用形容词，多用动词和数字。** "效果良好"→"查询 12 条记录耗时 3ms"。

对比：

| 别写 | 改写 |
| --- | --- |
| 本文基于 Spring Boot 框架构建了一个高内聚低耦合的学生管理系统 | 系统用 Spring Boot 写了三个模块：登录、学生管理、成绩查询 |
| 该方案显著提升了系统的可维护性 | 把数据库操作集中到 DAO 层，改表结构时只需要动一个文件 |
| 通过合理的设计，实现了数据的完整性 | 给 sc 表加了外键，插入不存在的学号会直接报错 |

## 三、实验总结：只讲部分，按初学者写

**篇幅**：200~450 字，2~4 段。
**内容**：只挑 2~3 个具体问题，写清"卡在哪 → 怎么试 → 结果如何 → 还有什么没解决"。
**口吻**：允许口语、允许承认不会、允许写"还没搞明白"。

### 结构模板

```
第一段：这次实验实际动手做了什么（1~2 句，不复述实验目的）
第二段：卡点一（现象 + 原因 + 怎么改）
第三段：卡点二（可以更短）
第四段（可选）：没做完的部分 / 下一步想试什么
```

### 正例

> 这次实验主要是把课上讲的 E-R 图转换规则真正写成了 SQL。刚开始建 sc 表的时候只写了普通主键，结果插数据时同一个学生选多门课就报错，后来改成 (sno, cno) 复合主键才通过，算是真正理解了"联系集的主键由两端实体主键组成"这句话。
>
> 另一个卡住的地方是删除课程的时候报外键错误，查了资料才知道要先删 sc 里的记录，或者在定义外键时加 ON DELETE CASCADE。我没有加级联删除，而是在删除前先清理选课记录，感觉这样更安全一些。
>
> 统计查询的 GROUP BY 写得还不太熟练，一开始把 cname 放在 SELECT 里却没有写进 GROUP BY，虽然 SQLite 不报错，但换成 MySQL 严格模式就会失败。后面补上了分组字段，查询结果和预期一致。总体完成了要求，但索引优化没来得及做，后续想试试给 sc 表的 cno 加索引看看执行计划有什么变化。

### 反例（不要这样写）

> 通过本次实验，我深刻认识到了数据库设计的重要性。在实验过程中，我不仅巩固了课堂所学的理论知识，而且提高了动手实践能力，为今后的学习打下了坚实的基础。综上所述，本次实验收获颇丰，圆满完成了实验要求。

问题：没有一句具体信息；全是套话；任何实验都能套用。

### 另外几种常见坏味道

| 坏味道 | 改法 |
| --- | --- |
| 把总结写成知识点罗列（"第一，主键……第二，外键……"） | 换成"我遇到的报错" |
| 结尾强行升华（"为我成为一名优秀的工程师奠定了基础"） | 删掉，或换成"下一步想做什么" |
| 全是表扬没有缺点 | 至少留一句"还没搞明白/没做完" |
| 通篇没有"我" | 改成第一人称叙述 |

## 四、去 AI 味的词表

写完后全文搜一遍，出现就换掉：

| 别用 | 换成 |
| --- | --- |
| 综上所述 / 总而言之 | （直接删，或"总的来说"） |
| 不仅……而且…… | 拆成两句话 |
| 显著提升 / 大幅优化 | 给出具体数字 |
| 赋能 / 闭环 / 抓手 / 维度 / 生态 | （实验报告里不该出现） |
| 深入探讨 / 全面剖析 | "试了一下"/"看了一下" |
| 旨在 / 致力于 | "目的是"/"想做到" |
| 具有重要的现实意义 | （删） |
| 完美解决了 | "能跑通了" |
| 极大地提高了效率 | "从 8 秒降到 0.3 秒" |

句式上还有个特征：**连续三段都是"首先……其次……最后……"**，读起来就是模板。打散它，按"遇到什么问题"组织段落更自然。

## 五、数字要具体

| 模糊 | 具体 |
| --- | --- |
| 数据量较大 | 1200 条选课记录 |
| 查询很快 | 0.03 秒 |
| 报了一个错误 | `FOREIGN KEY constraint failed` |
| 修改了配置 | 把 `max_connections` 从 151 调到 300 |
| 大概跑了十几次 | 跑了 12 次，其中 3 次失败 |

数字必须和截图对得上。对不上就是编造。

## 六、段落与排版习惯

- 正文段落 3~6 行，一段只讲一件事。
- 图前一句"这次运行的条件"，图后一句"从图上能看到什么"。
- 列表用于并列项（步骤、参数、测试用例），不要用列表写叙述。
- 中文标点用全角，英文术语两侧不加空格（"用 Spring Boot 写"而不是"用 Spring Boot  写"）。
- 段落之间不空行，靠首行缩进区分（脚本已处理）。

## 七、交稿前自查

- [ ] 全文搜 `//`、`#`、`--`、`/*`，代码块里应该一个都没有
- [ ] 搜"综上所述""通过本次实验""深刻认识"，应该是 0 次
- [ ] 总结里有"我"，有具体报错或行号，有至少一句"没搞明白"
- [ ] 每个数字都能在截图里找到
- [ ] 没有"本文""该系统显著提升了"这类论文腔
